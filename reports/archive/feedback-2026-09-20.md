# User feedback — 2026-09-20

Running feedback from testing the CIFAR training workflow. Append further items
here as they arise. Implementation and acceptance are recorded in the [implementation report](feedback-implementation-2026-09-20.md).

## 1. Configurable CLI progress frequency

**Status:** Implemented in PR #342; see the implementation report for acceptance.

Training currently prints progress every update, making the terminal too noisy.
Print routine CLI training progress every **N steps**, with a default of **100**.
Make this interval configurable through the UI.

Implementation should keep console reporting separate from metric collection,
checkpointing and image previews. Changing the interval must not alter training
or reduce the metrics available in the UI. Errors, lifecycle changes and final
status should remain visible immediately.

The implemented control persists per run and applies during active training at a
complete update boundary. It does not change numerical configuration or metric cadence.

## 3. Review termination and interruption behavior

**Status:** Implemented and fault-tested in PRs #341 and #342; see the implementation report for limits.

Evaluate SIGTERM, SIGINT and abrupt process death across training, checkpoints,
metric publication and the server. Define graceful termination at a complete
update boundary, bounded shutdown and recovery when graceful shutdown cannot
finish. SIGKILL cannot be handled; recovery must use the last complete durable
commit. Include termination during event writes and checkpoint publication.

Coordinate this work with the consistency contract in item 6 and the independent
server lifecycle in item 5.

## 4. Configurable server binding and explicit authentication mode

**Status:** Implemented in PR #337.

Default the server bind address to `0.0.0.0`, with an option to select another
address. Keep the token mechanism, but make it an explicitly selected mode via
`--auth token`, rather than mandatory authentication. Leave room for additional
authentication methods behind the same interface. Without an authentication
mode selected, the proposed default is unauthenticated access.

Binding, browser connection URLs and authentication selection should be distinct
settings; `0.0.0.0` is a listen address, not a browser destination.

## 5. Keep the server running after training ends

**Status:** Implemented in PR #339 with persistent viewing, reuse, status and explicit stop.

The owner observed that the server stops when training stops. Keep it available
after training ends so users can inspect metrics and samples. Define explicit
server shutdown and reuse/reconnection when training resumes, including normal
completion, bounded stops, failures and termination signals. Avoid duplicate
servers on successive training attempts.

## 6. Commit checkpoints with a durable metrics boundary

**Status:** Implemented in PRs #340–#342. The implementation report defines the accepted durability and projection contract.

When saving a checkpoint, flush the corresponding metric events to disk. A
published checkpoint should identify the exact durable event boundary matching
its saved training state. Improve eventual consistency without allowing the UI
projection's delay to make the underlying checkpoint/event record ambiguous.
This contract is closely tied to termination handling in item 3.

Proposed acceptance contract:

- Finish the complete training update and emit all events required for that
  checkpoint's boundary. Preserve configured metric cadence; a checkpoint does
  not require inventing observations for steps where metrics were disabled.
- Make the event prefix and checkpoint payload durable before atomically
  publishing a manifest or commit record that references both, with run/attempt,
  step and event cursor identities. A userspace buffer flush alone is insufficient
  for crash durability; define file and directory synchronization explicitly.
- Recovery selects the last complete valid commit. Events newer than that
  checkpoint may exist, but must not be presented as part of resumed history
  without the recorded attempt/checkpoint ancestry. Existing history is retained.
- Browser projections may catch up asynchronously; expose their progress relative
  to the committed boundary so stale views are distinguishable from missing data.
- Exercise failure between each publication stage, including disk-write failure,
  SIGTERM and forced process death. Never publish a checkpoint claiming metric
  events that are missing or incomplete.

The intended atomic unit is the published reference to durable state and its event
prefix. Separate files do not become a single filesystem transaction merely by
writing them consecutively. The implementation report and recovery guide record the established guarantees
and their platform limits.

## 7. Present Inception FID as an evaluation metric in step order

**Status:** Implemented in PR #338 with ordered evaluation metrics, separate protocols and preserved repeats.

The owner finds Inception FID useful, but its results currently appear in the
order 10k, 30k, 40k, 20k. Present it as another metric, identified as an
**evaluation metric**, with its values ordered by the evaluated checkpoint's
training step: 10k, 20k, 30k, 40k.

Integrate evaluation metrics into the normal metric browsing/charting experience.
Use the evaluated snapshot's step for placement, even when evaluation completes
later or results arrive out of order. Preserve evaluation provenance, protocol,
attempt ancestry and repeated evaluations; do not silently combine incompatible
protocols or overwrite results sharing a step. Show evaluation time separately
from the training step it measures. Sparse evaluation points should not imply
that FID was measured at every training update.
