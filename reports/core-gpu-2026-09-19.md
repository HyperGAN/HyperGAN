# GPU-first native training and whole-job fault acceptance

Date: 2026-09-19. Base: `9d93f6de018719c2606f797a488e7293d6db034a`. This session follows the owner's direction to use the two local GPUs and default user projects to GPU training. Three subagents implemented native CUDA execution, independently reviewed recovery/fault behavior, and tested actual two-GPU NCCL communication. [PR #317](https://github.com/HyperGAN/HyperGAN/pull/317) targets `develop`; no paid compute or release is part of this milestone.

## Delivered behavior

`hypergan new demo` now writes `training.device="cuda"`; `--device cuda:1` selects the second visible GPU and `--device cpu` explicitly creates a CPU fixture. Structural configuration and CLI help remain Torch-free. Requested unavailable hardware fails before a run directory is created. The existing programmatic `DEFAULT` and empty-recipe reference stay CPU fixtures; shipped CPU tests/examples now request CPU explicitly when creating project files.

The native loop owns one resolved CUDA device, moves component/prior/objective/batch tensors there, keeps the data RNG on CPU, and creates prior/penalty RNG streams on the selected GPU. Device work completes before the controller acknowledges an update. Runtime identity includes resolved device, visible GPU identities, CUDA/cuDNN versions and precision/determinism settings.

Complete checkpoints include global CUDA RNG and the current device alongside the existing model/prior/Adam/EMA/buffer/data/named-stream state. CUDA restore rejects incomplete RNG inventory and synchronizes before publishing a resumed attempt. This supports current-implementation recovery; no older-checkpoint compatibility was added. Preview rendering uses copied EMA state on CPU; portable inference is tested without visible GPUs. Observation and export preserve global/named RNG and selected device. Native progress callbacks retain their synchronous contract; replicated callback supervision is not silently advertised for native CUDA.

The controller obtains its initial environment identity from the configured adapter, preventing an initializing GPU run from being labelled CPU. Independent review also found that Torch 2.14's Adam graph-capture health check initializes CUDA even for CPU parameters. A local Adam subclass bypasses that check only when every parameter is on CPU; accelerator parameters retain the upstream check and optimizer math/state are unchanged. A cold-process test in the CUDA-enabled runtime proves that an explicit CPU run, previews and sampling do not initialize CUDA.

See [native CUDA usage](../docs/cuda.md) and the separate [GPU readiness report](gpu-readiness-2026-09-19.md). The two-GPU diagnostic exercises real NCCL collectives, first/second derivatives, rank-averaged gradients and linear Adam parity. It does not execute HyperGAN's full replicated GAN. Initial probes exposed NCCL diagnostic-wait delays after a collective timeout; all ranks were reaped by the outer supervisor. Both unsuccessful prompt-abort expectations and the later explicit bounded-diagnostic configuration are preserved.

## Whole-job persistence and partial-update gates

Six tests run the actual shared replicated controller with CPU world size two, accumulation two, shuffled data and stochastic components. Each establishes a complete checkpoint, injects one later fault, verifies failed status/worker reaping/lock release, and recovers exact complete rank state in fresh workers:

1. Rank-zero staging manifest write fails.
2. Parent rename to a canonical generation fails.
3. Parent latest-pointer write fails before selection.
4. Pointer replacement succeeds, then raises.
5. Rank one fails during the second generator microbatch backward after the discriminator update.
6. Rank one fails during EMA after the generator optimizer has updated.

The post-pointer case retains a valid newer checkpoint even though no successful save acknowledgement was returned. Its failed manifest records the prior acknowledged durable step; takeover reads the actual selected checkpoint and does not repeat its completed update. Other persistence failures retain the prior selection. Partial numerical updates are never acknowledged or snapshotted. These complete the fault gates left by the bounded-observation checkpoint without multiplying already-covered low-level failure matrices.
